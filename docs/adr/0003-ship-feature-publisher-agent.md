# ADR-0003: `ship-feature`를 Builder/Publisher 두 세션으로 분리 — Rule of Two 위반 해소

**상태**: accepted

## 컨텍스트

`ship-feature`는 이 플러그인의 단일 진입점이며, step 0(워크트리)부터 step 5(PR 오픈+이슈 코멘트)까지
**하나의 연속된 세션**이 끊김 없이 자율 실행한다(`SKILL.md` "Execution mode — autonomous by default").
그 한 세션 안에서 다음 세 가지가 동시에 성립한다:

1. **신뢰불가 입력 처리** — step 1(계획/`grill-with-docs`)과 step 2/4(구현/리뷰)에서 이슈 본문, 웹
   리서치, 서드파티 문서 등 외부·비신뢰 콘텐츠를 읽고 해석한다.
2. **민감 접근** — step 2~4에서 워크트리 전체에 대한 읽기/쓰기/코드실행 권한을 갖는다.
3. **외부 상태변경** — step 5에서 `git push`로 공유 브랜치에 새 참조를 만들고, PR을 열고, 트래커
   이슈에 코멘트를 남긴다.

Rule of Two(동시에 최대 2개)를 세 가지 모두가 동시에 성립하는 순간 위반한다. 위험 시나리오: step
1~4의 어느 시점에 처리한 비신뢰 콘텐츠(예: 이슈 본문이나 웹 문서에 숨은 prompt injection)가 같은
세션의 나중 판단에 영향을 남긴 채로, 그 **같은 세션이** step 5에서 push/PR-open/코멘트라는 실제
외부 행위를 실행한다 — 주입된 지시가 "무엇을 만들지"뿐 아니라 "무엇을 내보낼지"까지 오염시킬 수
있는 경로가 구조적으로 열려 있다.

이미 존재하는 완화책(`A human merges` 불변식, 서버단 브랜치 보호, 결정론적 리스크 게이트)은 전부
**머지/배포** 경계에 있다 — push·PR-open·이슈코멘트 자체는 이미 자율 실행되고 있고, 이번 이슈가
지목하는 위반은 정확히 그 지점이다.

## 결정

**`ship-feature`의 step 5(PR 오픈 + 이슈 코멘트)를 별도의, 최소 권한 `publisher` 서브에이전트로
분리한다.** step 0~4를 실행하는 세션("Builder")은 지금처럼 신뢰불가 입력을 읽고 워크트리에 대한
전체 쓰기/실행 권한을 갖되(①+②, Rule of Two 안), **더 이상 자신이 직접 push·PR-open·이슈코멘트를
실행하지 않는다.** 대신:

1. Builder는 step 2~4를 마친 뒤, PR에 필요한 모든 콘텐츠(브랜치명, PR 제목/본문 — 검증 결과·게이트
   판정 verbatim 포함, 트래커 이슈 ID, 코멘트에 남길 정확한 문구)를 **완성된 리터럴 문자열**로
   조립한다.
2. 이 플러그인의 새 서브에이전트 `publisher`(`agents/publisher.md`, `tools: Bash`만 부여)를 Agent
   툴로 새로 스폰하며, 위 리터럴 값들을 프롬프트로 그대로 넘긴다. `publisher`는 그 값을 실행할 정확한
   셸 명령(`git push` · `gh pr create` · 이 레포 트래커의 코멘트 명령)까지 함께 프롬프트에서 받아
   그대로 실행만 한다 — 스스로 파일을 읽거나(Read 없음) 계획을 다시 세우거나 새 콘텐츠를 만들지
   않는다.
3. `publisher`는 **자기 컨텍스트가 Builder와 별개인 새 세션**이므로, Builder가 앞서 처리했을 수 있는
   비신뢰 콘텐츠를 한 번도 직접 본 적이 없다 — 설령 그 콘텐츠가 Builder의 판단에 영향을 남겼더라도,
   실제 외부 행위를 실행하는 세션은 그 콘텐츠를 애초에 읽은 적 없는 별도 프로세스다. 이게 "같은
   세션 안에서 셋 다"라는 구조적 조건 자체를 깬다 — self-report(같은 세션이 "나는 안전하다"고
   스스로 판단)가 아니라 **실제로 다른 프로세스**라는 사실이 경계다(리스크 게이트가 이미 쓰는
   "self-scoring 금지" 철학과 동일선상).

`publisher`의 `tools:`는 `Bash` 하나로 최소화한다 — Read/Edit/Write/WebFetch를 주지 않아, 설령
Builder가 조립한 프롬프트 자체에 문제가 있더라도 `publisher`가 스스로 추가 파일을 읽거나 외부
콘텐츠를 새로 끌어올 수단이 없다. GitHub CLI(`gh`) 기반 트래커는 이걸로 충분하다. **MCP 기반
트래커(예: Linear)를 쓰는 레포는 그 레포의 `.claude/agents/publisher.md` 오버라이드에서
`tools:`에 해당 코멘트 MCP 툴 이름을 추가한다** — `risk-rules.json`을 로컬에서 레이어링하는 기존
패턴(ADR 없음, `SKILL.md` 리스크 게이트 절 참고)과 동일한 레포-로컬 확장점이며, 플러그인 자체를
특정 트래커에 결합시키지 않는다.

**Reader 존은 이번 변경 범위 밖이다.** step 1/4의 "3회 이상 grep/read면 Explore류 에이전트에
위임" 관행이 이미 읽기 전용 조사를 부분적으로 분리하고 있고, 이슈 #15가 지목한 위반은 구체적으로
"push/PR-open/코멘트가 Builder와 같은 세션에서 실행된다"는 지점이지 조사 단계 자체가 아니다 — 새
메커니즘 없이 이미 있는 관행으로 충분하다고 판단해 범위에서 뺐다(과설계 방지).

## 고려한 대안

- **step 5를 사람에게 완전히 넘긴다(자동 push/PR-open 자체를 없앤다)** — 기각. "PR 오픈까지는
  자율"이라는 이 플러그인의 핵심 가치(`SKILL.md` 표제 자체)를 포기하는 것이고, push/PR-open 자체는
  이미 되돌리기 쉬운 행위(머지 전이라 언제든 브랜치/PR을 지울 수 있음)라 사람 개입 비용에 비해
  얻는 안전이 작다.
- **같은 세션 안에서 "이제부터 publish 모드" 같은 플래그/마커로 자체 선언한다** — 기각. 같은
  프로세스의 self-attestation이라 리스크 게이트가 이미 피하는 self-scoring 문제와 동일 — 프롬프트
  주입이 그 플래그 판단 자체도 오염시킬 수 있다.
- **Reader/Builder/Publisher 3분할을 한 번에 전부 새 메커니즘으로 만든다** — 기각(과설계). Reader
  쪽은 이미 사실상 충족되고 있어 이슈가 실제로 지목하는 좁은 지점(Builder→외부행위 결합)만 고치는
  게 최소 변경.

## 재검토 트리거

- MCP 전용 트래커(코멘트에 CLI 경로가 아예 없는 경우)를 쓰는 레포가 늘어나면, `publisher`의
  `tools:` 확장 관행을 문서화된 1급 옵션(예: `setup` 스킬이 트래커 종류에 따라 자동으로 채워주는
  템플릿 변수)으로 승격하는 걸 재검토한다.
- 이 분리를 실제로 몇 차례 돌려본 뒤 Builder→Publisher 핸드오프 자체가 병목/버그의 원천으로
  드러나면(예: 조립한 문자열이 셸 이스케이프 문제를 반복적으로 일으킴), 핸드오프 형식을 프롬프트
  문자열 대신 임시 파일 하나(Publisher에 최소 Read 권한 추가)로 바꾸는 걸 재검토한다.
